# 聊天里的大代码块背景透明（v1.32.13）

## Why

用户反馈（2026-10-15，v1.32.12 交付后明确指示「**修吧**」）：
**聊天正文里的大代码块**（`_block_7gxqk_4` + `md-code-block`，实测 **`331x524`**，
占视口 **91.8% × 78.1%**）背景被抹掉 ⇒ **代码文字透出底层聊天正文**，可读性差。

这是 v1.32.12 明确**登记为「已知遗留」**、当时**故意不夹带**的一项。

## 侦察结论（实测，非推断）

| 项 | 实测值 |
|---|---|
| 目标 | `_block_7gxqk_4 md-code-block _card_7gxqk_107`，`331x524` |
| 内联 | **`transparent !important`** |
| computed | `rgba(0,0,0,0)`，**alpha = 0** |
| **原生** | **`rgb(249,250,251)`**（不透明浅灰），`nativeAlpha = 1` |
| `innerBig` | **2** |

### ⚠ 更正 lead 任务书里的一个前提

任务书记「面板打开时是 `0.45`、内联 `rgba(249,250,251,0.45)`」——**实测复现不出来**：
该实例的实际坏态是 **`transparent`（alpha=0）**。

**原因**：同屏有 **10 个** `md-code-block`，**类名与宽度几乎相同、只有高度不同**。
按算术（视口 `360x671` ⇒ 阈值 `180 / 335.5`）逐条对照**全部吻合设计**：

| 实例尺寸 | w>180 | h>335.5 | 实测 | 说明 |
|---|---|---|---|---|
| `233x182/163/125/144` | ✓ | ✗ | `0.45` | 走普通分支（正确） |
| **`331x524`（目标）** | ✓ | **✓** | **`transparent`** | 被大容器分支抹掉 ← 要修的就是它 |
| `331x182/87/296/144` | ✓ | ✗ | `0.45` | 走普通分支（正确） |

⇒ **是分支问题（被大容器 `transparent` 分支吞掉），不是「0.45 太薄」**。

### 另一个真实存在、本轮也一并治掉的坏态

幂等闸门 `a0<1 → continue` 会把「**还矮时被 apply() 写成 0.45、之后长高**」的实例
**永久定格**在 0.45 ⇒ **永远修不回来**。修法必须**放行闸门**（见下）。

### 同屏「透明内容块」全集 = 只有目标一个

面板打开时「原生不透明但当前非不透明」的元素**全集只有 3 个**：
`BynINW_frame`、`Dc7zOa_root`（均为壁纸通道/布局容器，红线）与**目标代码块**。
⇒ **没有别的表格/引用/图片容器也在透明**。

## What Changes

给玻璃化决策树新增一条**内容块**分支，与既有链**互斥**：

**判据（结构，不依赖 CSS-module 类名）**：
```
isCB = big && !isAnchor && nativeOpaque && (innerBig <= 2)
innerBig = 后代中「自身也超过 50%×50% 视口」的元素个数   （= 里面还套着几层大容器）
```

**实测对照（`innerBig`，面板打开态）**：

| 元素 | 尺寸 | `innerBig` | 性质 |
|---|---|---|---|
| `BynINW_frame` | 360x671 | **70** | 布局容器（壁纸通道，红线） |
| `BynINW_centerCol` | 304x671 | **42** | 布局容器（红线） |
| `Dc7zOa_root` | 304x671 | **41** | 布局容器（红线） |
| `_block_7gxqk_4 md-code-block` | 331x524 | **2** | **内容块（目标）** |

⇒ 量级相差 **20 倍以上**，判据稳健（不是「刚好卡住」）。
**实测 `wouldChange` 恰好 = 1**（只有目标元素），锚点命中 **0**；面板**关闭**态该谓词命中 0
⇒ **零行为变化**。

### ⛔ 一个被实测否决的判据（务必别用）

**「后代含 `pre`/`code`」是坏判据**：`Dc7zOa_root`（**布局容器**，`innerBig=41`）后代里
**也有** `pre`/`code`（整棵聊天树含代码块）⇒ 该判据把它一起命中
⇒ **`wouldChange` 变 2 且包含布局容器** ⇒ 布局容器变不透明 ⇒ 多层白叠
⇒ **直接复现 v1.32.6「壁纸整层消失」**。
**这是「同色陷阱」的实证**：`BynINW_frame` 与目标的原生色同为白系，
**不能靠语义/颜色区分，只能靠结构嵌套计数**。

### 分支顺序（三道护栏一字不动）

```
if (isOv && (ovRole || !big))                    -> 浮层 0.96        （v1.32.11，不动）
else if (big && isPanel && pm)                   -> 阅读面板 1.0     （v1.32.12，不动）
else if (big && isCB && pm)                      -> 内容块 1.0       ★ 新增
else if (big)                                    -> transparent      （壁纸通道，红线不动）
else if (!skipBg)                                -> 0.45
```

### alpha 取 1.0 的理由

它是**内容**（读者要长时间看代码），不是浮在背景上的装饰；且**应用原生就是完全不透明**
⇒ **1.0 是还原原生设计**，与 v1.32.12 阅读面板同构。

### 幂等闸门放行

```
if(!isOv && !(big&&isPanel) && !isCB && a0<1) continue;
```
⇒ 命中内容块的元素**不受「已半透明则跳过」限制**，坏态 B（定格在 0.45）也能被纠正。

### 代价控制

`innerBig` 计算与「剥内联读原生」**都只在 `big && !isAnchor` 成立时才做**（先廉价后昂贵）。

## 本轮不改（既定行为，非缺陷）

同屏 **8 个较小的 `md-code-block`（高度未过阈值）当前是 `0.45`** —— 按设计走普通分支，
**属正常行为**；用户反馈的是大的那个。要把它们也变实底需**另一条更宽的判据**，
**风险更高、收益无证据** ⇒ 本轮**按 lead 裁定不动**。

## Impact

- 受影响 capability：`companion-app`。
- 版本：1.32.12 / 78 → **1.32.13 / 79**（三处同步）。
- 只动这段注入，不做重构；三道护栏（`isPanel` / `isAnchor` / veil 按 id 排除）**一字不动**。
