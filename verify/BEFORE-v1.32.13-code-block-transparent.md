## 2. ⚠️ 为什么要"先侦察再改"（本轮真正的难点）

**"给它加底"这件事本身有现成机制（v1.32.12 的 `nativeOpaque` 前置），但缺少"该不该给"的判据。**

已知的**同色陷阱**（v1.32.12 血泪）：
- `BynINW_frame`（壁纸通道，布局容器）原生 **也是 `rgb(255,255,255)`**；
- `Dc7zOa_root`（聊天根，布局容器）原生 **也是 `rgb(255,255,255)`**。

⇒ **"原生不透明"完全无法区分"内容元素"与"布局容器"**。
若把判据放宽成"凡原生不透明的大容器都给底" ⇒ **布局容器全部变不透明** ⇒ 多层白叠 ⇒
**壁纸整层消失 = 直接复现 v1.32.6**。

⇒ **本轮必须找到一条"内容元素 vs 布局容器"的区分判据**，且**实测证明"改动面"足够小**。

## 3. 侦查必答清单（developer）

1. **目标元素当前实况**：class / 尺寸（占视口百分比）/ `getComputedStyle().backgroundColor` / **内联值**；
2. **剥内联看原生**：原生 alpha 是否真的 ≥1（是 `rgb(249,250,251)` 还是别的）；**读完必须还原**；
3. **祖先链逐层**（代码块 → `body`）：逐层 alpha **与 `background-image`**（含 `::before/::after`）；
4. **算术**：`w>vw*0.5`（`>180`）与 `h>vh*0.5`（`>335.5`）各是否成立 ⇒ 确认它**是否曾落进大容器 `transparent` 分支**；
   ⚠️ **注意矛盾**：v1.32.12 QA 实测它面板打开时是 **`0.45` 而非 `transparent`**
   ⇒ **必须解释清楚**（可能：注入时还没渲染到全高、或它命中了另一条分支、或尺寸随滚动变化）——
   **这个矛盾必须查清，否则修法建立在错因上**；
5. **可区分特征**：找出**能区分"内容块"与"布局容器（`BynINW_frame`/`Dc7zOa_root`）"**的结构特征
   （候选方向：是否含直接文本 / 子元素数量 / 是否祖先里还套着别的大容器 / 是否 `overflow` 非 visible /
   是否 `role`/语义标签（`pre`/`code`）/ 是否 `md-*` 内容类名）。**给出你的判据 + 实测的 `wouldChange` 列表**；
6. **同屏还有没有别的"透明内容块"**（表格、引用块、图片容器等）——**一并列出**，别只修代码块。
