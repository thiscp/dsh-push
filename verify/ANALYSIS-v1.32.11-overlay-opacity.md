## 2. 根因（行号对 `android-app/app/src/main/java/xyz/cpyh/dshpush/WebActivity.kt`；下述决策树为**改前**原文）

### 2.1 玻璃化注入的决策树（**改前** `:339-379`）

`apply()` 遍历 `div,main,section,header,aside,nav,button,textarea,input,ul,li`，对**每个**元素：

```
① 若 !m（computed backgroundColor 不匹配 rgb/rgba）      ->  continue（跳过）
② 若 alpha < 1（已半透明）                                 ->  continue（幂等：不重复处理）
③ 否则若 w > vw*0.5 && h > vh*0.5                          ->  'transparent'   ← 大容器＝壁纸唯一通道
④ 否则若 !skipBg                                           ->  'rgba(r,g,b,0.45)' + backdrop-filter:blur(12px)
```

其中：

```js
var skipBg = cn.indexOf('_2H3hWW_root') >= 0 &&
             cn.indexOf('_2H3hWW_collapsed') < 0 && vw <= 1023;
```

**⇒ `skipBg` 只豁免「窄屏 + 展开态侧栏」。**

### 2.2 两条闸门各自造成的后果（**这是理解本轮的关键**）

| 元素类型 | 撞上哪条闸门 | 改前结果 |
|---|---|---|
| **真实指令菜单**（表层 `rgba(0,0,0,0)`，底色来自样式表/伪元素） | 第 ② 步 `alpha<1` | **被跳过，从未被注入** ⇒ **完全没底色**（比 0.45 更糟）|
| 普通卡片（有不透明背景，如输入卡 `RlGAzG_card`） | 走到第 ④ 步 | 被压成 **0.45** |
| 展开态侧栏 | 第 ④ 步有 `skipBg`，另由 `bwPanelBg()` 单独设 | **0.92**（v1.32.5 单独救过）|
| `#dsh-theme-veil` | 第 ② 步 `alpha<1`（它自己就是 0.45） | 保持 **0.45**（**靠这条才没被改——见 §3**）|
| 大容器 | 走到第 ③ 步 | **`transparent`** |

**⇒ 所以"浮层太透"有两种成因**：菜单是**压根没底色**，dialog 之类是**被压到 0.45**。两种都得治。

### 2.3 为什么"加一条 CSS 规则"压不住

玻璃化用的是 **CSSOM 内联 `!important`**（`e.style.setProperty(..., 'important')`），
原因是**页面 CSP 拦动态 `<style>` 标签**（代码注释 `:336-337` 已写明）。
⇒ 内联 `!important` 优先级高于任何样式表；**必须像 `skipBg`/`bwPanelBg()` 那样，在注入逻辑内部跳过/改写**。

### 2.4 本仓已有的窄屏注入（另一条路径，别混淆）

`:270-328` 有独立的 `#bw-narrow-fix` 样式表注入（`@media (max-width:1023px)`），管的是侧栏浮层化、命中区尺寸等。
**它不负责不透明度**（不透明度全在 §2.1 的 CSSOM 路径里）。改本轮问题时别在错的那条路径上使劲。

## 3. ⚠️ 最大的风险：`#dsh-theme-veil`（tester `QA-A29` 点名）

同一个 `apply()` 里还创建/维护一个全屏纱罩（`:367-375`）：

```js
var v = document.getElementById('dsh-theme-veil');
if (!v) { v = document.createElement('div'); v.id = 'dsh-theme-veil'; document.body.appendChild(v); }
v.style.cssText = 'position:fixed;inset:0;z-index:-1;pointer-events:none;background:' +
                  (lum > 0.5 ? 'rgba(18,24,40,0.45)' : 'rgba(255,255,255,0.45)');
```

**它现在为什么没被 §2.1 的循环改掉**：它是 `div`，会被 `querySelectorAll` 选中，但：

1. 它自身 computed alpha = **0.45 < 1** ⇒ 改前撞决策树**第 ② 步 `continue`**，被跳过；
2. **改后**（developer 已把幂等闸门改为"**只约束非浮层**"）：它**必须不能**被判为 `isOv`，否则就会被提亮。
   我（lead）**独立沿新代码逐条走了一遍**，确认 veil **判不出 `isOv`**：
   - `cn.indexOf('BynINW_')` = **-1**（它 id 是 `dsh-theme-veil`，无 class）→ 进入候选；
   - `role` 属性 = **无** → role 分支不命中；
   - 几何分支：`position:fixed` ✅ 但 **`z-index:-1` → `parseInt('-1',10) = -1 < 10` ✗**（第一条就挡住）；
     且 `inset:0` ⇒ `w = vw, h = vh` ⇒ **`w <= vw*0.9` ✗**（第二条也挡住）。
   ⇒ **两道都不过 ⇒ `isOv=false` ⇒ veil 仍走第 ② 步被跳过，alpha 保持 0.45。** ✅
   （`z-index>=10` 与 `面积<=90%视口` 两条门槛，恰好是本轮护住 veil 的**结构性**原因，不是巧合。）

**⇒ 这就是本轮的雷**：如果新加的"浮层例外"规则**放宽到"凡是 `position:fixed` 就提亮"**
（或把判定放在幂等闸门之前、或去掉 `z-index`/面积门槛），veil 就会被提亮成接近不透明
⇒ **整张壁纸被盖住**，症状与 **v1.32.6 那次"壁纸整层消失"一模一样**。

**因此本轮的硬性验收要求**：
1. veil 的 alpha **必须仍是 0.45**（`QA-P12` 明确断言）；
2. 大容器（`BynINW_frame` / 中心列 / `html` / `body`）**必须仍 `transparent`**；
3. **必须看整页截图**——v1.32.6 的教训就是"只看面板截图看不出来"。

### 6.5 🔴🔴 根因钉死到**一行**（QA 实测 + lead 独立读码验证）——**分支顺序反了**

QA 判 **FAIL（P1）**：真菜单表层 **alpha = 0**（不是 0.92），内联被写成 `transparent !important`。

| 行 | 代码 | 说明 |

| `:394-398` | `else if(isOv){ …0.92… }` | **永远轮不到** |

**算术证据**（视口 `vw=360, vh=671`；真菜单 `257x392`）：
`257 > 180` ✓ **且** `392 > 335.5` ✓ ⇒ **落进大容器 `transparent` 分支**。

而**真实菜单 `257x392`（面积 >50%）落进了另一个分支**。
⇒ **合成用例的几何必须照真实元素设**（这是本轮最贵的一课）。

**修法**（已开 `task-8` 交 developer）：浮层判定提到大容器分支之前、两者**互斥**，**保留大容器仍 `transparent`**（v1.32.6 红线）：

```js
else if(w>vw*0.5 && h>vh*0.5)        { …'transparent'… }

```
**另**：tester 建议 `role` 命中的浮层（`menu|listbox|dialog|alertdialog|tooltip`）**直接豁免所有几何判定**——
真菜单正是靠 `role=listbox` 命中，几何分支从未被用到，反而被面积条件废掉。

**本轮 PASS 的正确基线（复修后必须复跑）**：`QA-P12` 壁纸通道（frame/centerCol/html/body 仍 `rgba(0,0,0,0)`）、
`QA-A29` **veil 仍 0.45**（tester 实测确认 0.45 —— **我 §3 的读码推演由此获得独立实测支撑** ✅）。

### 6.11 ✅ 结案：**不是构建问题，是"版本指纹在错误时刻被采集"**（2026-10-15 00:2x）

**lead 用 DEX 字面量比对做了决定性判定**（比看哈希/看命令行都硬）：

```
vm1 clean assembleDebug（16 executed，源码含 0.96）
  → unzip classes*.dex
  → strings | grep -c "0.96"              = 8      ✅ 新值已在字节码里
  → strings | grep -c "18,24,40,0.96"     = 1      ✅ 浮层回退纱色 = 0.96
  → strings | grep -c "18,24,40,0.92"     = 1      ← 这是 L643 **短提示条**（非本浮层），符合预期
```

⇒ **`cb1a4ce8…` 这个哈希就是 0.96 build**（DEX 里确有 0.96）。**构建没有问题**，我先前"构建可能没生效"的怀疑**被推翻**。

**那 tester Part A 的 `0.92` 与它记录的同一个哈希怎么解释？** —— 时间线还原：

| 时刻 | 事件 |
|---|---|
| 00:06–00:16 | tester 采集 Part A 数据（**当时设备上是 0.92 build**）→ 实测 alpha **0.92**，7/7 恒定 |
| 00:22:10 | developer **装机 0.96 build**（`G:\Android\dsh-push.apk` mtime） |
| 00:2x | tester **写报告时再读一次**已装 APK 的哈希 ⇒ 读到的是**已被替换成 0.96 的** `cb1a4ce8…` |

⇒ **Part A 的数据有效（就是 0.92 build 的行为），但报告里的"版本指纹哈希"是在采样之后才读的**，
**两者被错误地并列在同一张表里** —— 这是**版本指纹采集时机**的记账错误，
**与"构建没生效"是完全不同的两件事**（我一开始怀疑错了方向，用 DEX 比对纠正了自己）。

**⇒ 由此固化一条纪律（比 §6.11 初稿更准确）**：
**冻结 build 的哈希必须在采样前后各读一次（bracket），且必须与采样同刻**；
只写一个哈希而没有"何时读的"，就会出现"数据属于 A 版本、哈希属于 B 版本"的错配 ——
**而这正是本轮反复出现的"验了但验的不是那个版本"的另一种形态**。
