### 1.2 为什么这是**真缺陷**（不是洁癖）

1. **今天能用是"靠顺序"**：emulator 解析 `config.ini` 是**后者胜**，所以 L141–143 的 1440x3168@640 生效。
   但这也意味着**任何规范化/重写 config.ini 的动作都可能把重复键合并掉**——而 emulator **自己就会在某些 boot 上重写该文件**。
   一旦合并时保留了先出现的那份，几何就**静默回退到 1080x2400@420**，**整套 CSS360 基线当场作废**，且症状是"截图看着怪"而不是报错。
2. **`hw.gpu.enabled = no` 与"一律真 GPU"的约束直接冲突**：现在能跑真 GPU 只是因为自愈命令行**显式**带了 `-gpu host`。
   同样脆弱：任何走别的启动路径（`dsh-emu-sw` → `run-emu-sw.cmd`）的启动，就可能拿到 CPU 软渲染 —— 正是加固版自愈脚本 F2 要防的那件事。
3. 备份 `config.ini.bak-1440`（10-11）里**没有**这三行覆盖，说明覆盖是后来手工追加的，本来就是"补丁摞补丁"。

### 1.3 修法（脚本：`verify/laptop-avd-config-hardening.ps1`）

```
1) 备份            -> config.ini.bak-f4-<时间戳>
2) 三个 LCD 键各只保留【最后一条】（= CSS360 值 1440/3168/640），删掉更早的重复项
3) hw.gpu.enabled = no  ->  yes
4) 复核：每个键恰好 1 条、值对；打印 before/after 与行数变化
5) 全程不启停模拟器；改动在【下次冷启动】生效
```

支持 `-DryRun`（只打印计划、不改文件）。

## 3. F6：自愈阶梯缺机器可读输出（已取证，未改）

### 3.1 现状

- 判定"现在跑的是真 GPU 还是软渲染"目前有**两条**路：
  1. `verify/emu-gpu-verdict.ps1`（**本轮新增**，一条命令、exit `0`=PASS / `3`=SOFTWARE / `4`=BLOCKED）——**这是可判据的**；
  2. `G:\Android\emu-ladder.log` 的**人读文本**（`interactive console session: False`、`already healthy: …` 等）。
- 缺的是：**阶梯自己**在每轮结束时落一个**机器可读状态帧**（当前 rung、渲染器、几何、时间戳、是否 VIOLATION），
  这样看门狗/QA/agent 都能一条命令判，不必 grep 日志措辞。

### 3.2 为什么本轮不改

- `emu-selfheal.ps1` 是**现网关键路径**（每 5 分钟跑，负责把模拟器拉起来并纠正软渲染）。
  加固版（F1–F3）**刚在 20:00 通过真机验证**（37s 拉回真 GPU，`INFRA-HEALTH-2026-10-14.md` §9.7）。
  在同一个晚上再改它 = 让"已验证的现网状态"重新变成"未验证的现网状态"，**收益（日志更规整）远小于风险**。
- 而且已有替代品：**`emu-gpu-verdict.ps1` 就是那个"一条命令判据"**（含 `-SelfTest` 6 条合成用例、只读、不启停）。
  F6 想解决的问题（"别只能人读日志"）**已被这个脚本覆盖**——真正缺的只是"把它接进阶梯的收尾输出"。

### 3.3 建议方案（下轮，单独一轮 + 真机回归）

```
在 emu-selfheal.ps1 的每轮收尾追加一行 JSON 到固定文件（如 G:\Android\emu-ladder-state.json）：
{ ts, rung, renderer, gpu, geometry:{w,h,density}, verdict:"OK|VIOLATION|BLOCKED", action }
并让 emu-gpu-verdict.ps1 优先读该帧（缺失时回落到实时探测）。
验收：三种场景各跑一次（已健康 / 软渲染违规 / rung1 失败→救援），断言 JSON 的 verdict 与渲染器一致。
```
